# 0004 参考图直接随请求上传为 base64（取代早期的签名 URL 方案）

- 状态：**已推翻早期结论**，改为「压缩后纯 base64 随请求上传」（2026-11-19）
- 相关：05 图片创作、04 创作任务

## 背景

magpie 的图片 MCP 工具 `generate_image` 的 `reference_images` 只接受 http(s) URL 或 data URL
（源码里的 `imageMCPFrom` 常量），不接受本机文件路径，除非生图 agent 与 magpie 同机部署。
两条可行路径：把原图压缩后 base64 塞进请求体，或让 magpie 自己来拉一个短时 URL。

## 决策（2026-11-19 修订）

**改为纯 base64 随请求上传**，不再签发 URL。

推翻早期结论的原因：上游换成了 lxz 自己写的 magpie 插件 `magpie-image-edit`，
它的 `edit_image` 工具**本身就接受纯 base64 / data URL / http 地址 / 本机路径**，
并且**以 base64 回包**。既然字节本来就要双向过一遍请求体，再为「让上游来拉取」维护一套签名、
过期、可撤销的外链就是纯额外复杂度，还要求本服务对外可达。

尺寸核算：原图压缩到长边 1536、JPEG 质量 85 后单张约 150–250 KB，base64 膨胀约 1/3，
按「一图对一图」一次最多十张量级估算，单次调用请求体在数百 KB 到数 MB，远低于网关的请求体上限。

## 后果

- 收益：请求体不受图片体积影响（一张 10 MiB 原图 base64 后约 13 MiB，多图会直接撑爆网关的 body 限制）；
  不把图片字节写进任务日志或错误信息；图片过期后自然失效，无需清理。
- 代价：**部署约束** —— 生图服务必须能访问到本服务的地址（同一网络或经公网入口）；
  需要一套签名与过期校验，且要防止被当作通用文件下载器。
- 影响：部署文档必须写明「网关需要能访问本服务」，跨网络部署时要配置对应的入口地址。

## 备选与放弃原因

- data URL：实现最省，但请求体会随着原图数量线性膨胀，且图片不可控地经过网关的请求日志。
- 纯文生图（不送参考图）：就是第一版的做法——但这不是「图生图」的替代方案，而是另一个能力。

## 何时重启

打开图生图开关前，必须先完成本决策的实现与部署约束检查。
