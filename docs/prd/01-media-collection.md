# 01 媒体资源夹与原始文件

> 依赖：骨架与数据/API 契约 ｜ 产出：资源夹与原始图片的持久化能力

## 目标

把「一次素材收集」归档成媒体资源夹：名称、来源平台、来源链接、原始标题、原始文案，以及一组原始图片。
后续所有创作都基于资源夹进行，因此这里的文件生命周期必须可靠。

## 范围

包含：

- 资源夹的创建、查看、列表、编辑、删除。
- 原始图片多张上传、预览、解除关联、排序。
- 图片的鉴权读取（不通过 `public/` 暴露）。
- 删除资源夹时的级联清理。

不包含：

- 页面交互细节（列表、弹窗、图片网格的三种状态）属于「媒体资源夹页面」功能。
- 从外部平台抓取图片。

## 设计契约

### MUST

1. **资源夹允许没有图片**：用户可能先建夹再慢慢收集素材。保存时不校验图片数量；
   「至少要有一张原图」只在**发起创作**时校验（见 `docs/prd/04-generation-task.md`）。
2. 上传文件落盘路径由服务端生成（`<UPLOAD_DIR>/media-assets/<collectionId>/<uuid>.<ext>`），
   原始文件名只作为展示字段保存，绝不参与路径拼接。
3. 上传必须校验 MIME 类型与大小：只接受 `image/jpeg`、`image/png`、`image/webp`，
   单张不超过 `MAX_UPLOAD_BYTES`（默认 10 MiB）。判断类型以文件内容为准，不以扩展名为准。
4. `storage_key` 与业务记录解耦：解除图片与资源夹的关联不得删除磁盘文件，只删除关联记录；
   历史任务与结果引用的文件必须仍然可读。
5. 删除资源夹时，其任务、结果、发布记录随数据库外键级联删除；磁盘文件删除失败不得让请求失败，
   只记录日志，避免留下不可删除的脏记录。
6. 任何资源夹或图片读取接口都必须校验会话（走统一门禁），返回 404 而不是 403 以避免泄露存在性。

### SHOULD

- 资源夹存在「运行中」任务时，拒绝编辑图片集合与删除资源夹，返回 `CONFLICT` 并说明原因。
  这是为了避免为「任务进行中图片被移除」这种低概率场景引入引用计数机制。
- 列表接口统一使用分页信封（`items` / `total` / `page` / `pageSize`）。
- 上传接口返回已保存的资产记录（含可直接渲染的 URL），前端不必二次查询。

### MAY

- 图片排序字段 `sort_order` 可用拖拽调整；第一版能用「按上传顺序」即可。
- 资源夹封面取第一张原始图片，不单独存储。

### MUST NOT

- 不得把上传文件写进 `public/` 或任何随镜像分发的目录。
- 不得因为「图片已被某个历史结果引用」而阻止用户移除原图——历史结果自己持有生成文件。
- 不得引入引用计数、垃圾回收守护进程等机制来解决文件清理（单用户场景过度设计）。

## 数据与接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/collections` | 列表，支持 `q` 搜索、`status` 筛选、分页 |
| POST | `/api/collections` | 创建（字段 + 至少一张图片，multipart 或先上传后关联） |
| GET | `/api/collections/[id]` | 详情（含资产列表、任务数、结果数、状态） |
| PATCH | `/api/collections/[id]` | 编辑来源信息 |
| POST | `/api/collections/[id]/save` | 编辑保存：来源信息与图片变更一次提交（multipart） |
| DELETE | `/api/collections/[id]` | 删除，级联清理 |
| POST | `/api/collections/[id]/assets` | 追加图片（multipart，可多张） |
| DELETE | `/api/collections/[id]/assets/[assetId]` | 解除关联 |
| GET | `/api/files/[collectionId]/[assetId]` | 鉴权读取原图字节 |

编辑保存只有一个入口：`POST /api/collections/[id]/save`。表单里 `fields` 是整体替换的来源信息 JSON，
`assets` 是有序图片清单（`keep` / `remove` / `add`，顺序即新的 `sort_order`），每个 `add` 对应一个
`file:<tempKey>` 文件 part。服务端先完成全部校验再写盘，随后在一个事务里改字段、删关联、插新增、
更新顺序；事务失败会补偿删除本次新写的文件，库与磁盘都回到保存前的状态。
`PATCH /api/collections/[id]`、`POST · DELETE /api/collections/[id]/assets` 保留给其它入口与独立验收，
编辑弹窗不再调用它们。

资源夹状态（列表筛选用的派生值，不落库）：
`draft`（无结果且无任务）／`generating`（有运行中任务）／`has_results`（有结果未发布）／`published`（已发布）。

## 验收标准

| 编号 | 断言 | 自动化用例 |
| --- | --- | --- |
| AC-01-1 | 创建资源夹并上传 2 张图片后，列表与详情都能看到这 2 张图片 | `tests/e2e/collections.spec.ts` |
| AC-01-2 | **没有图片也能保存成功**；0 张图时「开始 AI 创作」置灰并提示先上传素材 | 同上 |
| AC-01-3 | 上传 `.txt` 或超限图片被拒绝，错误信息说明原因 | 同上 |
| AC-01-4 | 编辑资源夹只改来源信息时，已有图片全部保留（数量与内容不变） | 同上 |
| AC-01-5 | 解除某张原图关联后，该图从详情消失，其余图片不受影响；已存在的创作结果仍能打开其图片 | 同上 |
| AC-01-6 | 删除资源夹后，其任务、结果、发布记录在数据库与界面中都不再出现 | 同上 |
| AC-01-7 | 图片字节通过 `/api/files/...` 返回，`content-type` 正确；未登录（启用口令时）返回 302 或 401 | 同上 |
| AC-01-8 | 0 张图的资源夹调用 `POST /api/collections/[id]/tasks` 返回 `VALIDATION_FAILED`，不建任务 | 同上 |

## 验证方式

```bash
pnpm test          # service 层单测：校验规则、路径生成、级联删除的参数拼装
pnpm test:e2e      # tests/e2e/collections.spec.ts
```

通过条件：以上用例全绿，且 `pnpm build` 无错误。
