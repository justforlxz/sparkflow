# 0006 账号登录现在做，工作区维度晚点加

- 状态：已采纳（2026-11-17）
- 相关：11 账号与会话、骨架节点、未来的多工作区

## 背景

第一版就需要登录，不是「可选口令」；长期规划是按工作区组织、允许多个账号。
问题在于：现在就引入工作区维度，还是只做账号、把工作区留到真正需要时再加。

## 决策

**现在做账号与会话**（`user` 表、`session` 表、登录页、登出、密码重置命令），
**现在不建工作区维度**：业务表不带 `workspace_id`，查询不做工作区过滤。

工作区的引入路径写死在这里，避免将来各自发明：

1. 新增 `workspace`、`workspace_member` 两张表；
2. 一次迁移给所有业务表加 `workspace_id`，回填为默认工作区，再加非空约束；
3. 在服务层加一个「当前工作区」作用域函数，所有 repo 查询从它取 `workspace_id`；
4. 新增工作区切换器与成员管理。

## 为什么现在不加

- 现在只有一个账号、一个工作区，过滤条件恒为同一个值，写进每个查询只增加代码与测试负担，
  还会引入「忘了加过滤」这一类 bug。
- 回填是安全的：迁移时全部数据属于唯一的默认工作区，不存在归属歧义。
- 引入工作区时的改动是「一次迁移 + 在集中位置加过滤」，而不是散落各处的重写——
  前提是本项目的查询已经集中在各模块的 `repo.ts`（`docs/architecture.md` 已规定）。

## 后果

- 收益：骨架与后续节点不必为不存在的多租户付出复杂度。
- 代价：引入工作区时要再动一轮所有模块的查询层，这是可预期的、机械的工作。
- 约束：所有数据访问必须集中在模块的 `repo.ts`，不允许在页面或路由里直接写查询——
  否则第 3 步无法在一个地方完成。这条已写入 `AGENTS.md`。

## 备选与放弃原因

- 现在就加 `workspace_id`：为「可能发生」的需求扩大当前范围，违反本项目的范围纪律；
  且当前没有第二个账号，无法验证过滤是否正确。
- 完全不留演进路径：将来只能在页面里零散加过滤，风险更高。

## 会话与密码

- 密码用 Node 内置 `scrypt` 派生（无新依赖），哈希串里带参数与盐。
- 会话是数据库记录：cookie 里放随机令牌，库里存令牌的 SHA-256；因此「登出」「改密码」「踢下线」
  都能真正失效，而不是等签名过期。
- 会话有效期 30 天，不做滑动续期（少一条时间逻辑）。
