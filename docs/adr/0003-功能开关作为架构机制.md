# 0003 功能开关作为架构机制，而不是散落的 if

- 状态：已采纳（2026-11-17）
- 相关：10 功能开关、图生图、分享

## 背景

最初有两个「界面保留、能力不做」的功能：图生图与分享。2026-11-19 起 **图生图转为已实现**（见 ADR 0008），
只剩分享仍为未实现。如果按常规做法在各处写
`if (!implemented) return`，会出现三个问题：判定口径散落、接口可以被绕过、下一版要打开时要全库搜索。

## 决策

把「功能是否可用」做成一等概念：

1. 一份**开关注册表**（代码里的常量）：key、名称、说明、默认值、`implemented`、影响的界面与接口。
2. 一张**持久化表**保存用户/部署层的开关值，默认值取自注册表。
3. 一个**唯一判定入口**（服务端函数）供接口层、任务执行层调用；一个**唯一展示入口**
   （界面组件）供页面调用。任何地方都不得自己判断 `implemented`。
4. 设置页有一个真实的开关区块，读写的正是这张表。
5. 注册表里 `implemented = false` 的开关，服务端**拒绝**把它打开（返回明确错误），
   界面上显示为不可操作的「本版本未实现」。能力做完后把 `implemented` 改为 true 即生效，调用点不改。

## 后果

- 收益：口径单一、可被测试断言（接口层拒绝 + 界面提示 + 无网络请求）；下一版打开图生图只需
  实现能力并把 `implemented` 改为 true，不碰调用点。
- 代价：多一张表、一个模块、一个界面区块；开关数量多了以后需要定期清理不再使用的 key。
- 边界：功能开关不用于 A/B 测试，也不用于按用户分流——本项目只有单用户。

## 备选与放弃原因

- 环境变量开关：部署期无法在界面里改，且与本项目「配置都在库里」的约定冲突。
- 各调用点自行判断：见背景，三个问题都无法避免。
