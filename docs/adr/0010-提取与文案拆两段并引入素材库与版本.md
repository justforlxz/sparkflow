# 0010 提取与文案拆成两段，引入素材库与文案版本

- 状态：已采纳（2026-11-20）
- 取代：ADR 0008、ADR 0009 中「一条任务跑完提取与文案、结果与任务一对一的」部分

## 背景

现状是一条 `generation_task` 同时含「提取（image）」与「文案（copy）」两个阶段，跑完产出一个
`generation_result`，结果与任务一对一。提取目标只有一个（资源夹上的单值字段）。

真实使用暴露三个问题：

1. **提取产物种类不够**：一次只能出一个目标（如桌垫纹理），要边框样式就得再建一个资源夹。
2. **两件事被绑死**：想先看看提取效果、再决定文案怎么写，做不到——点了就得全跑。
3. **没有版本**：改一版文案就覆盖一版，回不到上一版，也说不清「这一版用哪几张图」。

## 决策

### 1. 两个独立动作，不再是一条任务的两个阶段

| 动作 | 触发 | 产出 |
| --- | --- | --- |
| AI 处理（提取） | 资源夹里勾选原图 + 选类别 → 发起 | `library_asset`（进素材库） |
| 生成文案 | 发布页里选素材 → 发起 | `copy_version`（新版本） |

原 `generation_task` / `generation_stage` 的「两阶段」结构不再使用，由 `extraction_run` 取代提取侧。

### 2. 提取按「类别」产出，一图多类

内置两类：`material`（材质纹理）、`border`（边框样式），登记表在常量里（像 `styles.ts`），
加第三类只改一处。提取粒度是 **原图 × 类别**：勾选 N 张原图、选 M 个类别 → 最多 N×M 次调用，
产物各自成为一条素材。允许部分失败（成功的进库，失败的记原因）。

### 3. 素材库独立于「结果」

`library_asset` 属于资源夹，带 `category` 与 `source_asset_id`（这张素材来自哪张原图）。
素材不再挂在某个文案结果下——同一张素材可以被多个文案版本引用。

### 4. 文案按版本记录

每次「生成文案」产生一个 `copy_version`，`version_no` 在资源夹内递增。
版本固化两件事：**当时生成的标题/正文/标签** 与 **当时选中的素材 id 列表**。
素材选择不单独版本化——它已经是版本的一部分，再拆一层只会让组合爆炸。

### 5. 发布记录改挂文案版本

`publish_record` 从「挂 `generation_result`」改为「挂 `copy_version`」，并记录发布时采用的素材快照。
发布仍然是用户手动点「标记为已发布」，不做 AI 自主发布。

### 6. 一次性迁移，不留双模型

数据量极小（3 个资源夹、个位数结果），一次性把历史数据迁到新模型：

- 每个历史 `generation_result` → 一条 `copy_version`（`version_no = 1`，
  `selected_asset_ids` 取该结果下生成图的 `source_asset_id`）；
- 每个历史 `generated_asset` → 一条 `library_asset`（`category = other`，界面归到「其他（历史）」）；
- 每个历史 `generation_task` → 一条 `extraction_run`（终态照搬，`categories = [other]`）；
- `publish_record.result_id` → `copy_version_id`。

迁移后旧表删除。**不保留「旧模型只读」的第二条路径**——每个页面都兼容两套模型的长期成本，
远高于一次性迁移的成本。

## 后果

- 收益：提取与文案各自可重跑；素材可复用；文案可回看版本；产物按类别组织更好挑。
- 代价：一次结构性迁移 + 四个页面的重构；`generation_task` 相关的状态机、进度、重试逻辑要在
  `extraction_run` 上重做一遍（不复用旧表，避免半新半旧）。
- 风险：迁移不可逆。迁移前必须先在真实库上跑一次演练并把结果写进验收记录。

## 备选与放弃原因

- 保留两套模型：页面要同时兼容新旧数据，长期每个查询都要考虑两套，维护成本高于迁移。
- 素材选择也版本化：组合爆炸，且用户心智里「版本」指的是文案，不是选图。
- 类别做成数据库表由用户维护：第一版只有两类，常量登记表足够；真要扩展再迁移成表。
