# 0012 总资源库与资源夹的相册模型，文案功能下线

- 状态：已采纳（2026-11-24）
- 修订：ADR 0010（资源夹与素材的关系）、PRD 01 / 06 / 08 / 12

## 背景

ADR 0010 把「资源夹」当成素材的唯一归属：`media_asset.collection_id` 非空，删资源夹级联删照片。
真实用法不是这样：**照片先集中收在一处（总资源库），再按风格归到不同资源夹（相册）**。
同一张照片可能同时属于「桌垫」和「夏日桌面」两个夹；从夹里移除也不该把文件从总库删掉。

同时，提取结果现在按「处理类型」分组展示（材质纹理 / 边框样式），
用户要的是**按每张原图看结果**——一张图的三类产出并排，才看得出这张图拆出了什么。

另外，文案与发布功能在真实使用里没有被用到，先下线，把范围收窄到「收集 → 提取 → 看结果」。

## 决策

### 1. 照片池化：`media_asset` 不再属于资源夹

```
media_asset                 -- 总资源库（照片池）
  id, storage_key, file_name, mime_type, size, created_at
  （删除 collection_id 列）

collection_asset            -- 资源夹 ↔ 照片 多对多
  collection_id, asset_id, sort_order, added_at
  primary key (collection_id, asset_id)
  on delete cascade（删夹只删关联行，照片留在池里）
```

- **多对多**：一张照片可以同时属于多个资源夹（相册语义）。
- **删夹不删照片**：只删 `collection_asset` 关联行；照片只能从总资源库显式删除。
- **上传入口两条**：总资源库直接上传（只入池）；资源夹内「添加」（入池 + 建关联）。
- 提取运行仍挂 `collection_id`（一次提取属于一个夹，输入是这个夹里的照片）。

### 2. 提取结果按原图分组

界面从「按类别分组」改为**按原图一张卡**，卡内并排三类产出。
数据不变（`extraction_item` 已经有 `source_asset_id` + `category`），只是渲染口径变了。

### 3. 文案与发布功能下线

删除：`copy_version`、`publish_record` 两张表与 `src/modules/copy-generation`、`src/modules/publish`、
`/published` 页面、侧栏「发布记录」项、相关接口。
删除前先 `pg_dump` 备份；历史数据不迁移（这两张表只有开发期测试数据）。

### 4. 资源夹页布局

- 容器放宽到 **1200px**（全站唯一例外，其余页面仍是 `max-w-5xl` 1024）。
- 宽屏（≥1240px）三栏：左 232 素材 / 中 620 结果 / 右 268 设置；**整页锁高度，只有中列滚动**。
- 窄屏（<1240px）回落单列流式，页面滚动，顺序：素材 → 结果 → 设置。
- 三列统一用 `Panel` 卡片（14px 圆角、`--line` 描边、单档阴影）；结果卡不再自带阴影。

## 后果

- 收益：照片不再重复上传；一个夹里移除不影响别处；结果按图看，能判断「这张图值不值得用」。
- 代价：多一张关联表；`media_asset` 的删除语义从「随夹删」变成「显式删」，需要额外确认弹窗。
- 风险：迁移时若历史照片没有归属夹，会变成「只在总库」的照片——这是预期行为，但要在迁移脚本里
  明确写出「不删除任何照片行」。

## 备选与放弃原因

- 一张照片只属于一个夹（`collection_id` 可空 + 唯一约束）：无法表达「同一张图进多个风格夹」。
- 复制照片到每个夹：磁盘重复、删除语义混乱。
- 保留文案功能只删界面：代码与表留着会持续产生迁移与测试成本，且没人用。
